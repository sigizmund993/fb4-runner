# fb4-runner

Программа на Raspberry Pi робота FootBot4: принимает команды стратегии по UDP, переводит их в UART-команды для STM32 ([прошивка](https://github.com/SPbUnited/FootBot4_Firmware)), пересылает телеметрию STM32 и мяч с бортовой камеры обратно стратегии.

```bash
make run          # без видеострима
make run-stream   # со стримом rtsp://<RPi>:8554/ball
make test-udp     # печатать команды, приходящие по UDP (main.py остановлен)
make test-uart    # тестовые команды в UART (дриблер, езда, поворот) и телеметрия STM32; робот на подставке
make flash-fw     # залить на STM32 релиз прошивки из CI (FB4_FW_RELEASE)
```

Процессы (`src/main.py`): приём SSL vision, `command_receiver` (UDP :5555 → UART, 100 Гц), `telemetry_transceiver` (UART → UDP broadcast :5556).

## Данные между процессами

`main.py` создаёт объекты и передаёт их в процессы аргументами; при старте процесса каждый объект копируется, общим остаётся только то, что лежит в общей памяти или у сервера `Manager`.

Общие:

| Что | Механизм | Пишет → читает |
|---|---|---|
| `robot_id` | `multiprocessing.Value("i")` | `telemetry_transceiver` (принимает id от STM32) → `command_receiver` (ищет себя в vision, шлёт id в UART) |
| `coefficients_crc` | `multiprocessing.Value("I")` | `command_receiver` (хранит коэффициенты из стратегии) → `telemetry_transceiver` (кладёт в `raspberry_status` телеметрии) |
| `VisionClient._detections`, `_packages` | `multiprocessing.Manager().list()` — отдельный процесс-сервер, каждое чтение идёт через сокет с пересылкой всего кадра | `Vision_Receiver` → `command_receiver` (`Field.update()`, `get_robot()`) |
| `/ball_shm`, `cx, cy` в пикселях (uint16) | POSIX shared memory | детектор мяча на Hailo (`yolo26_post.cpp`, запускает `run.sh`, отдельная программа) → `BallDetector` в `command_receiver` и `telemetry_transceiver` |

Копии (у каждого процесса свои):

| Что | У кого | Следствие |
|---|---|---|
| `BallDetector`: `p_pos`, `r_pos` | `command_receiver`, `telemetry_transceiver` | Оба сами вызывают `update()` и считают мяч из `/ball_shm` независимо: мяч в телеметрии и мяч для RICOCHET/CATCH_BALL могут расходиться на кадр |
| `VisionClient`: настройки, multicast-сокет, `_robot_detection_time` | `Vision_Receiver`, `command_receiver` | Сокет читает и `_robot_detection_time` ведёт только `Vision_Receiver`; `command_receiver` берёт из клиента только общие списки выше |

## Настройки (.env)

Настройки робота лежат в `.env` в корне репозитория. Файл не в git, у каждого робота свой; шаблон с описанием переменных — `.env.example`. Если `.env` нет, `make run`, `make run-stream` и `make flash-fw` создают его копией шаблона; существующий файл не перезаписывается, поэтому переменные, добавленные в шаблон позже, в него сами не попадут — до тех пор действуют значения по умолчанию. Переменная, заданная в окружении (`FB4_ROBOT_TEAM=blue make run`), перекрывает файл.

| Переменная | По умолчанию | Что это |
|---|---|---|
| `FB4_ROBOT_TEAM` | `yellow` | `yellow` или `blue`, для поиска робота в SSL vision |
| `FB4_UART_PORT` | `/dev/ttyACM0` | порт STM32 |
| `FB4_RICOCHET_CAM_GAIN` | `5.0` | RICOCHET и CATCH_BALL: наименьшая скорость [1/с] на метр промаха поперёк траектории мяча |
| `FB4_KICKER_FACE_X` | `0.10` | RICOCHET и CATCH_BALL: x центра мяча при ударе в системе робота [м] |
| `FB4_CAM_EXPOSURE_US` | `5000` | экспозиция камеры [мкс], ручная; `auto` — автоэкспозиция. Короткая меньше размывает летящий мяч (за 30 мс мяч на 2 м/с проходит 6 см) и даёт кадр свежее. Читает `run.sh` |
| `FB4_CAM_GAIN` | `8.0` | аналоговое усиление камеры при ручной экспозиции (IMX219: 1..10.7); если картинка тёмная и мяч не детектится — больше, если шумная — меньше и экспозицию длиннее |
| `FB4_FW_REPO` | `SPbUnited/FootBot4_Firmware` | репозиторий прошивки |
| `FB4_FW_BRANCH` | `feature/uart_for_rpi` | ветка прошивки |
| `FB4_FW_RELEASE` | `latest` | `latest`, номер релиза ветки (`5` или `v0.0.5`) или полный тег |

Читает файл `src/utils/envfile.py` (только stdlib: `flash_firmware.py` работает без venv). Другой файл можно подсунуть через `FB4_ENV_FILE`.

Прошивка: `make flash-fw` берёт `FB4_FW_BRANCH` и `FB4_FW_RELEASE`; разово можно `make flash-fw RELEASE=5`, `make flash-fw BRANCH=main RELEASE=latest`, `ARGS=--dry-run` — только найти и скачать. Если на STM32 уже этот образ, повторно не пишет.

## UART с STM32

Код: `src/protocol/uart.py`. Парная сторона — `src/devices/uart_control` в прошивке; форматы должны совпадать.

Кадр в обе стороны: `[0xA5][payload][XOR от 0xA5 и payload]`.

| Направление | Формат | Поля | Кадр |
|---|---|---|---|
| RPi → STM | `<5eB??B` | vel_x, vel_y, w, dribbler, kicker [В] (fp16), kicker_mode, angle_mode, beep, robot_id | 16 байт |
| STM → RPi | `<Be??` | robot_id, напряжение кикера [В] (fp16), ball_deep, ball_front | 7 байт |
| RPi → STM, настройки | `<8f` | angle_k, angle_b, max_linear_vel, max_linear_accel, max_angular_vel, max_angular_accel, wheel_vel_p, wheel_vel_i (float32); NaN — по умолчанию | 34 байта, синхробайт `0x5A` |

Если формат меняется, прошивку, раннер и teleop надо обновлять вместе: кадры другой длины не распознаются, и робот стоит. Кадр настроек teleop не шлёт; старая прошивка его пропускает как мусор.

## Коэффициенты регуляторов (SET_COEFFICIENTS)

Стратегия может менять коэффициенты на лету: команда `SET_COEFFICIENTS` с сообщением `Coefficients` (`robot/control.proto`). Это не команда движения: раннер применяет коэффициенты и продолжает текущую команду. Каждая команда — полный набор: незаданное поле — значение по умолчанию (`config.py` у раннера, прошивки — какое было при загрузке STM32).

- Раннер хранит последний набор в `coefficients.json` в корне репозитория (не в git) и загружает при старте. Чтобы вернуть значения по умолчанию, удали файл и перезапусти раннер.
- Поля STM32 (`angle_k`, `angle_b`, ограничения скорости и ускорения, PID скорости колёс `wheel_vel_p/i`) раннер отправляет кадром настроек по UART сразу и потом раз в `SETTINGS_RESEND_S` (1 с): STM32 их не хранит и после сброса получает снова. Прошивка пишет в лог только изменения (`Settings from the RPi`), PID колёс отправляет моторам по CAN тоже только при изменении.
- Остальные только у раннера (`src/tuning.py`): `position_kp`, `position_max_vel` (езда в точку по vision для GLOBAL_COORDINATES и RICOCHET), `ricochet_gain`, `catch_gain`, `onboard_max_vel`, `kicker_face_x`, `min_approach_vel`, `freeze_s` (см. «RICOCHET и CATCH_BALL»). Изменения печатаются в журнал (`coefficients: ...`).
- В медленной части телеметрии (`raspberry_status`, раз в секунду) `coefficients_crc` — CRC32 сохранённых коэффициентов (по имени, значение во float32). Стратегия (`FB4_COEFFICIENTS` в `strategy/bridge/const/coef_const.py`, всегда полная таблица) шлёт `SET_COEFFICIENTS` всем роботам при своём старте, сразу после `RobotCommand.set_coefficients` (OPTIMIZE_PID) и роботу, у которого CRC не совпадает с её, не чаще раза в 2 с (робот, включённый позже). Таблица стратегии перекрывает `FB4_RICOCHET_CAM_GAIN` и `FB4_KICKER_FACE_X` из `.env`. Формулу CRC менять в `tuning.coefficients_crc` и в стратегии вместе.
- Каждый `SET_COEFFICIENTS` заменяет весь набор: поля, которых в нём нет, а также NaN и отрицательные значения берутся по умолчанию (как в прошивке).

## Напряжение кикера

Везде вольты на конденсаторе:

- команда: `KickerAndDribbler.kicker_voltage` (uint32) — цель заряда 0..330 В, `0` — не заряжать. Раннер ограничивает её `KICKER_MAX_V` (330) и передаёт в UART как есть; прошивка ограничивает ещё раз;
- `OldFormat.kicker_setting` остался уровнем 0..15: раннер переводит 1..15 в 100..330 В (`kicker_setting_to_voltage`);
- телеметрия: `StrategyTelemetry.kicker_voltage` (float) — измеренное напряжение.

Раньше `KickerAndDribbler` нёс уровень 0..15 в поле `kicker_setting`. Номер и тип поля те же, так что старая стратегия не сломается при разборе, но её 0..15 теперь означают вольты (робот почти не заряжается); после перегенерации proto имя поля в её коде надо поменять на `kicker_voltage` и слать вольты.

## beep

`RobotCommand.beep` (поле 11, вне `oneof`) работает с любым типом команды и уходит в STM32 битом `beep`. Писк длится, пока приходят команды с `beep = true`; когда стратегия замолкает (`CMD_TIMEOUT_S`), он прекращается вместе с движением.

## robot_id и hostname

Id робота хранится только в hostname RPi (`fb4-NN`, в mDNS — `fb4-NN.local`). В `.env` его нет, STM32 его не сохраняет: после загрузки у неё id нет (на экране `--`), она берёт id RPi с первого кадра.

- При старте id — `NN` из hostname `fb4-NN`. Если hostname другой, id = 0 и RPi переименовывается в `fb4-00`.
- RPi шлёт свой id в каждой команде. STM32 берёт его сразу, кроме случая, когда id на роботе поменяли кнопками.
- `telemetry_transceiver` берёт id STM32, если тот отличается от своего дольше `ROBOT_ID_ADOPT_S` (1 с), и меняет hostname (`hostnamectl`, `/etc/hosts`, перезапуск avahi; нужен root). Задержка даёт STM32 время взять id RPi при подключении и не переименовывает RPi на каждом нажатии кнопки, пока id перебирают.
- Текущий id делят процессы через `multiprocessing.Value`. `command_receiver` подхватывает новый id на лету: шлёт его в UART и ищет в SSL vision робота с этим id.
- После смены id стратегия и teleop должны обращаться к новому `fb4-NN.local`.
- Поменять id без кнопок: `hostnamectl set-hostname fb4-NN` на RPi и перезапуск раннера.

## RICOCHET и CATCH_BALL

- RICOCHET едет в `(x, y)` по SSL vision и держит `angle`; без `angle` держит курс, с которым пришла команда. CATCH_BALL поворачивается на `angle` на месте.
- Точку и угол для отскока считает стратегия. Робот только подправляет себя по бортовой камере, чтобы мяч попал в центр кикера. Мяч может прийти под любым углом, поэтому робот выравнивается по траектории мяча, а не по его текущему y.
  - **Точка траектории** — мяч с последнего кадра камеры, если он ближе `CAM_TRUST_DIST` (0.6 м). Дальше камера ошибается в расстоянии (гомография подогнана по полю рядом с роботом; на 1.5 м — на 30% ближе), и точка берётся из SSL vision: мяч в системе робота по позе робота из vision. Если vision не видит мяч или робота — снова камера.
  - **Камера** не видит мяч позади робота (x < 0) и дальше `CAM_MAX_DIST` (2.5 м): это ложные детекции выше горизонта, там гомография даёт что угодно.
  - **Направление** — скорость мяча из SSL vision, повёрнутая в систему робота по его курсу из vision. Она на поле (движение робота её не искажает) и отфильтрована на всём пути мяча, поэтому есть уже с первого кадра камеры.
  - **Без vision** (vision не видит мяч или робота дольше `VISION_TIMEOUT_S`, например робот заслонил мяч) и при сбое скорости из vision (быстрее `BALL_MAX_VEL` = 8 м/с или больше чем на `BALL_DIR_TOL_DEG` = 45° от направления по камере) направление и точка — прямая по кадрам камеры за последние `BALL_PATH_S` (0.2 с, не меньше `BALL_PATH_MIN_FRAMES` = 3 кадров), метод наименьших квадратов. Робот при этом сам едет, поэтому старые положения мяча сдвигаются на его перемещение по заданной скорости.
  - **Когда.** Пока мяч летит к кикеру — его скорость к центру кикера больше `RICOCHET_MIN_APPROACH_VEL`, 0.3 м/с. Если мяч перестал «лететь» (пропал на кадр, сбой), робот `COMING_HOLD_S` (0.15 с) стоит, а не уезжает в `(x, y)`.
  - **Как движется.** Робот едет **только поперёк траектории мяча**, вдоль неё не едет. Скорость = gain × промах.
  - **Промах** — расстояние по нормали от траектории до точки `(FB4_KICKER_FACE_X, 0)`: центр мяча при ударе, 0.10 м, как `ROBOT_R` в стратегии.
  - **Запаздывание робота.** Скорость робота догоняет команду примерно через `ROBOT_RESPONSE_S` (0.1 с). Поэтому промах берётся предсказанным на это время вперёд с текущей поперечной скоростью робота из vision, и закрывается он на `ROBOT_RESPONSE_S` раньше.
  - **gain** не меньше `FB4_RICOCHET_CAM_GAIN` (5 1/с) и растёт так, чтобы закрыть промах за `RICOCHET_FREEZE_S` + `ROBOT_RESPONSE_S` (0.15 с) до удара. В эти последние 0.15 с новые команды не успели бы подействовать, и робот их не даёт (скорость 0).
  - Курс робот не меняет: держит `angle`. Пока робот поворачивается, траектория считается неверно: к приходу мяча он должен уже стоять под нужным углом.
- Пока мяч не летит к кикеру, RICOCHET едет в `(x, y)`, а CATCH_BALL едет вбок к текущему y мяча с камеры (`vel_y = FB4_RICOCHET_CAM_GAIN × y`).
- Скорость не больше `RICOCHET_MAX_VEL` (2 м/с), направление при этом сохраняется.

### Лог

`command_receiver` пишет CSV по строке на тик (100 Гц), пока идёт RICOCHET или CATCH_BALL, и ещё 0.5 с после, чтобы был виден исход (`cmd` = `after:<команда>`). Один файл на запуск раннера, `logs/ricochet_<дата>.csv` (не в git), хранятся последние 20. Колонки описаны в `src/ricochet_log.py`:

- команда стратегии (`cmd_x/y/angle`), робот по vision (поза и скорость), мяч по vision и возраст его последнего кадра (`vball_age`);
- мяч с камеры: пиксель, положение в системе робота, `cam_new` — новый кадр, `path_frames` — кадров в `BallPath`;
- траектория (`line_*`): `line_src` — откуда точка и направление (`camera/vision`, `vision/vision`, `camera/fit`), точка, скорость, `coming`, промах, время до кикера; `mode` — `align`, `freeze`, `hold` или пусто (команда как есть);
- что ушло в UART; `dt` — время с прошлого тика (0.01, если цикл успевает).

Забрать с робота:

```bash
scp 'root@fb4-NN.local:/root/fb4-runner/logs/ricochet_*.csv' .
```

## Калибровка камеры

Пиксель мяча → метры в системе робота: развёртка fisheye (`src/to_real_coords/camera_params_fisheye.npz`, по шахматке) и гомография плоскости поля (`homography_matrix.npy`). Гомографию можно подогнать по SSL vision: vision даёт мяч и робота на поле, камера — пиксель мяча.

1. На RPi, с запущенным детектором (`fb4-runner.service` или `run.sh`); `main.py` можно не останавливать:
   ```bash
   make calib-record            # TEAM=blue ID=3, если не из .env/hostname
   ```
   Мяч в поле один, лежит. Робот (teleop) встаёт так, чтобы мяч оказался в разных местах кадра: ближе, дальше (камера видит примерно до 1 м), слева, справа, по краям. На каждом месте стоять ~1 с: берутся только моменты, когда мяч и робот неподвижны 0.5 с. Пишется `calib_data/<дата>.csv` (не в git); в консоли раз в секунду счётчики — `rows` должен расти.
2. Подгонка (на RPi или на ноуте, скопировав csv):
   ```bash
   make calib-fit                         # все файлы calib_data/
   make calib-fit DATA=calib_data/x.csv SAVE=1
   ```
   Печатает ошибку старой и новой гомографии на этих данных по дальности (медиана, p90 в см) и точки, отброшенные RANSAC. `SAVE=1` перезаписывает `homography_matrix.npy`; раннер подхватит её после перезапуска.

Точность ограничена vision (~1 см) и курсом робота: 1° — 1.7 см на 1 м. Если ошибка новой гомографии растёт к краям кадра, виновата развёртка fisheye, а не гомография.

## Протобуфы

`ssl_packet_package` — сабмодуль (ветка `telemetry_for_feedback`), сгенерированный код в git не лежит:

```bash
make -C ssl_packet_package init build
```

- После изменения `.proto` (например, нового поля `beep`) `build` нужно перезапустить и на RPi.
- venv сабмодуля привязан к своему пути: после переноса каталога скрипты в `venv/bin` ссылаются на старый путь, и `build` падает с `protoc-gen-mypy: program not found`. Помогает `rm -rf ssl_packet_package/venv` и снова `make -C ssl_packet_package init`.
- Версии в `requirements.txt` сабмодуля не закреплены. Свежий `mypy-protobuf` требует protobuf новее установленного (`VersionError: ... gencode 6.x runtime 5.x`), тогда: `ssl_packet_package/venv/bin/pip install mypy-protobuf==3.6.0`.

## Автозапуск на RPi (systemd)

`/etc/systemd/system/fb4-runner.service`:

```ini
[Unit]
Description=fb4-runner
# Не ждём network-online: раннер стартует параллельно с подключением Wi-Fi
# (подписка на SSL vision повторяется, телеметрия без сети отбрасывается).
# Ждём только UART к STM32 и сервис Hailo.
After=fb4-firmware-updater.service hailort.service dev-ttyACM0.device
Wants=dev-ttyACM0.device

[Service]
Type=simple
User=root
WorkingDirectory=/root/fb4-runner
ExecStart=/usr/bin/make run
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Если `FB4_UART_PORT` не `/dev/ttyACM0`, поменяйте `dev-ttyACM0.device` на своё устройство.

Обновление прошивки при загрузке — `fb4-firmware-updater.service` (`Type=oneshot`, `ExecStart=/usr/bin/make flash-fw`, `After=network-online.target`). Чтобы раннер ждал его, добавьте `fb4-firmware-updater.service` в `Wants=` раннера. Сейчас на fb4-05 он выключен.

Время загрузки: `systemd-analyze`, `systemd-analyze blame`, `systemd-analyze critical-chain fb4-runner.service`.
